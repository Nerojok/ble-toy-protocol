# 星织（COC）BLE 控制协议笔记（实测，不是猜测）

一台国产蓝牙情趣设备（产品名「星织」）的控制帧格式。**所有结论都是抓包 + 实机写入验证过的**，没验证的都标成「未确认」。

写这份的原因很土：想找同类设备的协议参考，搜不到。自己啃完了，就放出来给下一个人省几个晚上。

> **范围**：只有「怎么让它动」。**没有**任何个人数据、设备序列号、配对记录。
>
> **性质**：非官方、未获厂商授权的独立研究。与设备厂商没有隶属或背书关系，也不包含官方客户端源码、安装包或固件。
>
> **状态**：实验性。照表操作前请先确认设备状态，并保留实体停止方式。

---

## 一句话结论

```
写通道      fe02（handle 0x000c），20 字节定长帧
帧结构      [通道][0x12][参数][0x00][附加][ …… 补 0 到 20 字节]
可用通道    0x01 震动模式 / 0x02 吸吮模式 / 0x03 震动强度
读通道      fe01、ff14 从不返回数据 → 这台设备没有可读的传感数据
```

完整帧表见 [`protocol/frames.md`](protocol/frames.md)。

---

## 怎么验的（这段比结论重要）

1. Android 开发者选项里打开「蓝牙数据包日志」，复现 App 的每次操作
2. `adb bugreport` 取 `btsnoop_hci.log`
3. `tshark -r btsnoop_hci.log -Y "btatt.opcode == 0x52"` 解出所有 Write Command
4. 按 handle 归并方向，发现真正在被写的是 `0x000c`（特征 `fe02`），不是我一开始猜的 `ff15`
5. 用 Python + bleak 逐帧重放，观察机械反应

**踩过的坑**：一开始我按"服务的写特征"去写 `ff15`，写了 15 种裸命令全无反应——因为那个特征根本不参与控制。**别信"哪个特征看起来最像写通道"这种直觉，去看抓包。**

## 最小可用代码

```bash
pip install -r tools/requirements.txt
python tools/ble_probe.py scan                 # 找设备
python tools/ble_probe.py gatt  <ADDR>         # 列出服务与特征
python tools/ble_probe.py write <ADDR> 03 12 80 00 00
python tools/ble_probe.py listen <ADDR> 30     # 看它会不会主动通知
```

写 `fe02` 时必须 `response=True`（Write Request 而非 Write Command），否则设备不认。

## 证据等级（认真对待这一栏）

| 结论 | 等级 | 依据 |
|---|---|---|
| 写通道是 `fe02` / handle 0x000c | **实测** | 抓包里 625 条写全在它上面；重放有效 |
| `03 12 XX` 是强度、线性 | **实测** | `20/80/FF` 递增，`00` 立即停 |
| `01 12 NN` 是震动模式（0–4） | **实测** | 节奏随 NN 变化 |
| `02 12 NN` 是吸吮模式（0–5） | **弱** | 当时设备还在真空包装里，机械受限，听感不可靠 |
| 设备能回传压感/力度 | **否** | `fe01`/`ff14` 从未返回数据；唯一通知是 10 秒一次的 `64 00 00` |
| `ff15` 也能控制 | **否** | 15 种裸命令 + 7 字节帧，零反应 |
